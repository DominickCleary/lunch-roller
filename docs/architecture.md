# Architecture

## Shipped local MVP

Next.js serves the interactive wheel, participant picker, wallet and administration UI. API adapters validate shared Zod schemas and call `GameService` in `packages/db/src/operations.ts`. `GET /api/v1/health` returns 200 only when PostgreSQL is reachable and settings row 1 exists; failures return safe 503 JSON. It checks initialization, not exhaustive schema compatibility or scheduler progress.

The worker checks the database and processes today's due draw every 30 seconds, emits structured logs, and optionally writes a health timestamp. Ticks do not overlap. SIGINT/SIGTERM wakes idle waits; bounded in-flight work finishes before shutdown. Configured push delivery runs in concurrent batches of ten with ten-second send timeouts. Missing or invalid VAPID settings disable delivery while retaining scheduling.

The pure domain package calculates odds, selects from an injected [0,1) sample, halves weights, applies influence, computes mean new-place weights, validates spending and evaluates explicit instants against local schedules. Contracts declare request/response schemas. The database service composes these calculations with authoritative persistence and server cryptographic randomness.

## Package dependency direction

`web → contracts, domain, db`; `worker → contracts, domain, db, web-push`; `db → contracts, domain, Drizzle, postgres`; `contracts → Zod`; `domain → nothing`.

Do not import web/worker into packages. Shared application operations live in the database service and compose pure domain functions. Web and worker use the same mutation implementation. Workspace source exports are intentional: Next transpiles them; the Node worker runs through pinned tsx. The DB package depends on domain/contracts as well as Drizzle/postgres.

## Transaction boundary

1. Begin transaction and acquire `SELECT ... FOR UPDATE` on settings row 1. All game mutations use this same first lock; the tiny workplace workload favors simple serialization over throughput. Resolve the live draw/attendance clock after acquiring this lock so a request waiting across local midnight cannot draw the previous date or award expired attendance. Tests can inject explicit instants.
2. Resolve participant/place status and idempotency. Derive balances from the ledger under the lock. Identical replay returns the exact recorded JSON response; reused key with a changed canonical request hash returns 409. Internal replay metadata changes only HTTP creation status, never wire data.
3. Apply validated writes together. Draw: check due date, read active options, select, insert snapshot/result, settle any open betting market against that exact pre-decay snapshot, halve winner, insert per-subscription outbox records. Purchase: insert debit and change weight/create place. Attendance: insert attendance and reward ledger entry. Betting reserves/release stake and records each idempotent request separately so edits that move only the selected place can be retried safely.
4. Commit before responding or delivering push. Database unique keys provide the last guard against duplicates. No external calls inside the mutation transaction.

One settings row is seeded and constrained to ID 1. Daily date uniqueness is intentionally global for the single workplace. Ledger request keys are unique per participant; attendance is additionally unique per participant/draw and its reward ledger row references attendance uniquely. Archived records retain foreign-key references. Wallet and today reads use read-only repeatable-read snapshots. Connection statements are bounded to ten seconds; write transactions use eight-second statement and three-second lock timeouts.

Admin participant removal uses the same settings-first transaction. It deletes only profiles with no attendance, ledger, added-place or subscription references; otherwise it archives and retires notification work. Foreign keys guard against references inserted outside the shared mutation path. The wheel-first UI keeps admin tools in a secondary disclosure and confirms removals before calling this operation.

Token economy settings live on the same settings singleton: attendance reward, new-place price, separate boost/reduce prices and weight multipliers. The admin setter validates the complete object and uses the game mutation lock. Each new attendance/purchase reads its configuration under that lock after checking for an idempotent replay. Replays return the original persisted response, and public today reads expose the economy from the same snapshot as live odds. This preserves historical token amounts, draw snapshots and saved-timezone attendance deadlines when an admin edits prices or rewards.

Admin balance setting computes a correction against the participant's ledger sum inside the settings-first transaction, and stores the requested result and reason in the idempotent ledger receipt. Restaurant percentage edits require the complete active set and replace its log weights in one settings-first transaction. A concurrent draw or place/economy mutation therefore sees either the old or the new distribution, while committed draw snapshots remain immutable.

Bet markets snapshot their scheduled local date, timezone, draw time, and admin-configured cutoff. The UI displays current fair fractional odds `(1-p)/p : 1` and estimated gross/net return; only a draw commit settles bets, using the saved pre-decay probability. Stake reservations, refunds, payout ledger entries, bet outcomes, draw snapshot, winner decay, and push outbox insertion share the settings-first draw transaction. Per-participant bet-request receipts preserve idempotency even for place-only edits. Schedule edits refund and void every open market before applying new dates; expired no-draw markets are refunded without catch-up draws. Banning a restaurant refunds its pending influence and open stakes without affecting unrelated positions. Disabling a participant refunds their pending influence and open stakes but preserves history.

Influence shares the betting market and its saved cutoff. Each new unit has an `influence_lots` row referencing its original debit, with saved token cost and logarithmic multiplier. The live restaurant weight includes its effect immediately. Withdrawing a unit before cutoff appends a `boost-refund` or `reduce-refund`, reverses the saved effect and marks the newest matching unit withdrawn; it never rewrites the debit. All market setup, position reads and mutations use the common settings lock. Mutation clocks are resolved after acquiring the lock. Ledger receipts provide idempotency for every edit, and all participants' counts come from authoritative unwithdrawn units. Settled market units retain their effects permanently and cannot be withdrawn. No historical unit rows are inferred from old purchases.

Schedule voids, expiry without a draw and participant deactivation refund affected pending units using the same inverse operation. A ban refunds affected units and bets even after cutoff, because the restaurant is removed from the undrawn wheel. Admin exact-odds overrides refund pending influence before replacing effective weights, so later withdrawals cannot distort the override. Additions/bans remain immediate final purchases. Daily read-only activity snapshots expose outstanding units grouped by person, restaurant and staged/locked/committed state for a draw date, separately from gross purchase/refund events by action date.

## Health balance and transfers

Places persist a checked three-value `health_level`, default Balanced. Settings hold an enabled flag and health multiplier, default true and 1.25. The pure domain `postDrawWeights` computes winner halving plus the healthy-place bonus only for Treat winners. In the same draw transaction, selection and bet settlement use the original pre-change probabilities; the server then persists updated weights and a `health_bonus` receipt on the draw. New snapshot entries retain ratings. Legacy snapshots remain untouched, with no inferred bonuses. Daily activity reads these receipts separately from token spending, and presentation compares the post-halving distribution immediately before/after the health bonus. Admin rule/rating edits take the common settings lock and affect future draws only.

Transfers use the common settings-first transaction and sender-scoped ledger idempotency. They validate active sender/recipient, different identities, whole positive amount and available ledger balance, then insert equal debit/credit rows with a shared transfer UUID, reciprocal participant references, and saved counterpart names in reasons. A unique transfer/direction index and signed-direction constraints guard record shape. Both rows commit or neither does; recipient credits never mint a net balance. Credits cannot be replayed as outgoing requests. Existing archive rules retain referenced people. UI confirmation precedes the existing persistent pending-request mechanism, so network retries reuse the original key.

## Shared wheel animation

Draw views derive animation v1 from immutable stored draw data, without a schema change. `wheelLandingRotation` maps the existing cryptographic selection sample into the saved winning segment, clamps exact borders by at most 0.3 degrees (or 2% of a small slice), and maps the point to the wheel’s right-side pointer. A stable SHA-256 of the draw ID chooses 9–12 turns and 18–21 seconds. The shared start is drawnAt + three seconds. No extra random selection, live weights, browser randomness or ledger mutations enter the plan. Historical reads and replays derive identical metadata.

Today reads include serverTime. The client estimates the server clock at the request midpoint and advances it with performance.now, keeping incorrect local wall clocks out of animation timing. A single pure cubic friction function maps absolute elapsed time to rotation; requestAnimationFrame updates only the wheel DOM transform, avoiding a React render on every frame. Late loads, refreshes and background-tab returns catch up rather than restart. Near a due pending draw and during the live reveal, visible tabs poll only today at one-second intervals; ordinary roster/wallet polling stays at 30 seconds. Visibility wake refreshes the clock. Network/clock estimation and render cadence can produce small timing differences; all clients use exactly the same trajectory and final landing.

The hook isolates saved animation segments from changing future odds, cleans up frames/timers/media listeners, and returns to the current baseline after a replay. Replays always begin at zero and use click-relative monotonic time. Reduced-motion preferences skip rotation and preserve the same landing. Normal live reveal hides the result footer/name and health-bonus card until completion; the API and other game records are still authoritative and readable. This is suspenseful presentation, not delayed settlement or access control.

## Identity and transport

Store the participant ID as `lunch-roller.participant-id` in localStorage, send it as `X-Participant-Id`, and validate that the participant is active. It is identity selection, not authentication. Reset stale selection when an ID is inactive or unknown.

The Team token activity disclosure uses the existing wallet read for a viewed active member. Its local viewed ID is scoped to GET requests and never changes browser identity, check-in or purchase state. Reads reuse the authoritative repeatable-read wallet snapshot; no additional API, permissions or database writes are introduced. Polling is limited to an open disclosure with a selected person, and cancelled/stale responses cannot replace the current person's display.

Wallet reads now join each ledger row to its retained restaurant and optional betting market, and include the participant's saved bets separately. This captures the latest selection even when a bet edit had no ledger delta. The daily activity tab uses a selected-participant-authorized read-only snapshot of all team ledger actions on a chosen calendar date in the settings timezone and all bets scheduled for that draw date. It includes archived actors/targets for continuity. No market creation or cleanup runs on these reads. Chart totals are recorded token spend, not inferred changes in historical probability. Daily polling runs only while the tab is mounted; date changes cancel requests and reject stale responses.

New installations initialize settings only and start with `setup_completed=false`. First-run administration uses the same separate password session to configure the empty roster, places and schedule. Completion locks settings first, requires an active person and place, and is persistent and idempotent. Public game/member APIs reject incomplete setup; worker draws and notification claims wait. Existing populated installations are marked complete by the additive migration without changing history. The UI validates saved browser identity before showing the wheel; new or stale identities must select a roster name, and Change name returns to that gate.

Admin login validates `ADMIN_PASSWORD` on the server with timing-safe comparisons and issues a signed eight-hour HttpOnly, SameSite=Strict cookie using a minimum 32-byte `SESSION_SECRET`; Secure follows HTTPS `APP_ORIGIN`. Participant IDs never authorize admin access. State changes reject missing or mismatched Origin headers. Login has a bounded process-local attempt limiter; use one web process or an external shared limiter before scaling. Passwords and session tokens are never logged.

Use polling for today's result initially; avoid a realtime service until needed. Public odds show current weights for the next draw; saved results contain pre-decay historical odds. A worker outage delays drawing, not the UI's authority over selection.

The server also derives `todayResponse.wheel` inside the same read snapshot. Pure `wheelDisplay` uses the workplace's local clock, calendar weekdays and persisted wheel switch time (default 15:00): a saved today result remains the baseline until that time, then live odds target the next scheduled date. An undrawn scheduled day remains pending even after the cutoff. Calendar date arithmetic uses UTC only as a calendar representation, never a 24-hour shift of a zoned instant; DST and skipped weekdays do not move the cutoff. This presentation change does not write draws, freeze odds, change attendance deadlines or alter the worker schedule. The browser uses the server mode/date and returns from historical replay to the live baseline.

Preferences contain the switch time, public check-in pledge, and betting close minutes (default 5); writes require admin authorization and take the settings lock first. Each market snapshots the close setting when created. `today` reads preferences and wheel metadata in the same repeatable-read snapshot. A separate participant attendance-status read checks the current draw and saved-timezone window without changing history. The UI binds that status to both person and draw, immediately disables a successful check-in, and reloads status for returning browsers. Attendance POST hashing/replay, ledger writes and uniqueness constraints remain unchanged.

## Scheduling and delivery

Calculate the current local date/weekday/time from the IANA timezone each tick; do not add 24 hours to UTC timestamps. Compare against the configured local time and existing date record under the transaction lock. A skipped spring-forward time becomes due at the first later local time; a repeated autumn time still draws once. No options is retryable without an empty draw record.

Outbox rows deduplicate on draw/subscription. Claims use `FOR UPDATE SKIP LOCKED`, a 60-second lease and a per-claim UUID. Completion checks the UUID so old workers cannot finish a reclaimed job. Retry with bounded exponential delay; stop after five attempts, including a crashed fifth lease, recording the failure. HTTP 404/410 retires the subscription and its remaining jobs. Archiving participants, changing subscription keys/owner and unsubscribing invalidate pending leases. Delivery is at least once: a crash after sending can cause duplicate push. A stable draw-ID notification tag reduces visible duplicates. Shared validation restricts subscriptions to supported browser push service hosts to prevent arbitrary internal HTTPS requests.

## Local deployment and operations

Compose supplies PostgreSQL, one-shot migration and settings initialization services, web, and worker. Dependency conditions ensure the database is initialized before readiness probes. Data uses a named volume. Images retain workspace dependencies to keep this first scaffold simple; optimize production size later.

Initialize the settings singleton after migration, then complete first-run setup through the administrator UI. Provision an always-on host, managed backups and tested restore, HTTPS reverse proxy, strong database/admin/session secrets, and VAPID keys before rollout. Do not expose PostgreSQL publicly. Use a one-shot migration release step before app startup. Check web readiness and worker heartbeat independently; readiness does not imply first-run setup is complete.

Monitor stale heartbeat, overdue scheduled draws, failed outbox jobs and migration errors. The [operations runbook](operations.md) covers configuration, rollout, monitoring and backup/restore. This repository provisions no hosting; production HTTPS and real-device push checks remain environment dependent.
