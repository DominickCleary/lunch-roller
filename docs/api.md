# API contracts

Base: `/api/v1`. Zod schemas in `@lunch/contracts` are the source of wire shapes. IDs are UUID strings; timestamps are ISO UTC strings; dates are `YYYY-MM-DD`. JSON errors use `{ error: { code, message } }`. All endpoints below are implemented. Responses are not cached.

## Implemented

`GET /health` → `healthResponse`: `{ status: 'ok' | 'unavailable', database: 'ok' | 'unavailable', service: 'web' }`. HTTP 200 when initialized and reachable, otherwise 503. No credentials/details and no caching.

## Shared wheel presentation

Draw responses include optional `animation: {version:1,rotation,turns,durationMs,startsAt}`. Current server responses always include it; it remains optional in parsing for older DTOs/test fixtures. Rotation is the final clockwise CSS wheel angle in [0,360), aligning a point inside the committed winning segment with the right-hand pointer. StartsAt is saved drawnAt plus three seconds; turns is 9–12 and durationMs is 18,000–21,000. The metadata derives deterministically from the persisted sample, snapshot, draw ID and timestamp and never changes on reread/replay. It cannot select or reroll a winner. Legacy records need no migration or historical rewrite.

GET `/today` includes optional `serverTime` (ISO UTC; always supplied by the current server). Clients anchor a monotonic clock to this server timestamp to share the live animation phase, independent of local wall-clock errors. Current server time changes on each read; the draw animation does not. The UI polls this read-only endpoint each second around a due draw/reveal and refreshes it when a hidden tab becomes visible. Committed results remain readable during presentation. Replay uses the saved plan on a local timeline and writes nothing.

## Game and administration endpoints

POST `/transfers` accepts `transferRequest: {recipientId,amount}` with active `X-Participant-Id`, matching Origin and UUID `Idempotency-Key`. `amount` is a whole number from 1 to 2,147,483,647. Returns `transferResponse: {transferId,recipientId,recipientName,amount,balance}` (sender’s resulting available balance). Self-transfer is 400 `SELF_TRANSFER`; inactive identities are 403, missing recipient 404, insufficient available balance 409 `INSUFFICIENT_TOKENS`, changed-body key reuse 409 `IDEMPOTENCY_MISMATCH`. A retry returns the saved response without moving more tokens. Matching `transfer-sent`/`transfer-received` ledger rows retain `transferId`, `counterpartyId`, signed amount, and saved counterpart names in `reason`; wallet and daily activity reads expose them.

GET/PUT `/admin/health-rule` reads/replaces `healthRuleSettings: {enabled,multiplier}` with admin authorization and matching Origin on PUT. Defaults true and 1.25; multiplier must be finite, greater than 1 and at most 100. `TodayResponse.healthRule` exposes current configuration. Place creation accepts optional `healthLevel:'treat'|'balanced'|'healthy'` (default balanced), and admin PATCH place accepts a rating change. Place responses and current odds expose the rating. Public creation can choose a rating but editing existing ratings requires admin. Draw snapshot entries save the rating used; legacy entries may omit it. Draw results include nullable `healthBonus: {multiplier,places:[{placeId,name,probabilityBefore,probabilityAfter}]}`. The chances compare the distribution after winner halving before/after the bonus. GET `/activity` includes `healthBonuses:[{drawId,placeName,drawnAt,bonus}]` for the chosen draw date, separately from token entries. Saved ratings/bonuses never change after a draw.

GET/PUT `/admin/economy` reads/replaces the complete `economySettings` object with admin authorization and matching Origin on PUT. Fields and defaults: `attendanceReward:10`, `addPlaceCost:20`, `removePlaceCost:40`, `boostCost:5`, `reduceCost:5`, `boostMultiplier:1.25`, `reduceMultiplier:0.8`, `newPlaceMultiplier:1`. Token amounts are whole numbers from 1 to 2,147,483,647; boost multiplier must be greater than 1 and at most 100; reduce and new-place multipliers range from 0.01 to 100 (reduce remains below 1). Multipliers affect relative weight, not probability percentage points. A new or restored restaurant starts at the arithmetic mean of active weights times `newPlaceMultiplier` (1 means the current average). `TodayResponse.economy` exposes current settings for member labels. Updates and game actions serialize on the settings lock, so each action uses one complete configuration. Prices/rewards in action responses are authoritative. Existing ledger entries, draw snapshots and idempotent replay responses retain their original values.

GET `/admin/token-balances` returns all people, including disabled people, with their ledger-derived balances. POST `/admin/token-balances` accepts `{participantId,balance,reason}` and sets an exact nonnegative target balance. It appends the difference as a reasoned correction; it does not edit past ledger rows. Balance targets are bounded by the token ledger's 32-bit entries. The write takes the settings lock first, calculates the difference from the locked ledger balance, rejects no-op targets, and supports `Idempotency-Key` so a retry cannot add another correction.

GET `/admin/restaurant-odds` returns every active restaurant's current wheel share. PUT accepts `{places:[{placeId,percent},...]}` for the complete current active set. Values must be positive and total 100% (within 0.01 for decimal entry); the API normalizes the submitted total and stores its logarithm as the relative weight. The settings lock serializes this update with draws, member purchases, archive/restore and place creation. Missing/stale restaurant lists are rejected. Existing draw snapshots are unchanged.

GET/PUT `/admin/preferences` reads/replaces `{wheelSwitchTime:'HH:mm',checkInPledge:string,bettingCloseMinutes:number,wheelSpinSeconds:number,postDrawDelayMinutes:number,maxWalkMinutes:number}` with separate admin authorization and matching Origin on PUT. `wheelSwitchTime` is retained for compatibility and no longer affects behavior; it is absent from the admin UI. Post-draw delay minutes is an integer 0–1440 (default 0 when omitted); 0 opens activity immediately after the draw. Pledge text is trimmed, 1–500 characters; close minutes is 0–1440 (default 10 for new installations). Maximum walk minutes is an integer 1–120 (default 15 when omitted); this public restaurant eligibility rule is checked by the team, alongside lunch opening hours. Spin seconds is an integer 5–60 (default 20 when omitted) and is saved on each new draw; previous draws keep their duration. `TodayResponse.preferences` exposes these public settings in the same snapshot as the wheel state; Schedule is unchanged. The cutoff is snapshotted when a betting market opens, so edits affect future markets.

GET `/setup` returns `{ completed, participantCount, placeCount }`. POST `/admin/setup/complete` requires the existing administrator session and matching Origin, requires at least one active person/place, and completes first-run setup atomically. It returns the same status shape with 200; incomplete configuration is 409 `SETUP_INCOMPLETE`. Until completion, public/member game endpoints return 403 `SETUP_REQUIRED`; administrator configuration, setup status, health and push configuration remain available. Runtime initialization creates no sample people or places. Existing populated installations are marked complete by migration.

Participant calls use `X-Participant-Id`; no member authentication is claimed. Admin calls use a separate server-verified cookie. Do not implement admin authorization through the name picker.

Participant removal returns 200 and removes the person from the active roster. Profiles with no attendance, ledger, influence, bet, added-place or subscription references are permanently deleted. Referenced profiles are archived instead, preserving history and retiring subscriptions/pending jobs; disabling or archiving also refunds the participant's pending influence and open bet stakes. Unknown IDs return 404. Repeated removal of an archived profile returns the same archived outcome. Reactivation remains an explicit admin PATCH operation.

Attendance, purchases, member place creation, and corrections require `Idempotency-Key` (UUID). Member ledger keys are scoped to the affected participant. Store a hash of method, route, and canonical validated body. Same key and body returns the recorded effect without repeating writes; changed body returns 409. Attendance has a second deduplication boundary on participant/draw; a fresh key must not award again.

Bets reserve stake from the participant's balance. One bet per participant and scheduled draw can be edited or cancelled until its saved cutoff. Request idempotency is stored separately from the ledger because changing only the selected restaurant may not create a balance delta. Settlement runs in the draw transaction against the committed pre-decay odds snapshot. A winning bet receives `min(2,147,483,647, floor(stake / actualProbability))` tokens as gross return (including the reserved stake); losses receive no payout. The UI's expected gross return uses current odds and can change before the draw. Restaurant banishments refund that restaurant's pending influence and open bets atomically; schedule edits refund all pending influence/open bets before changing the schedule.

GET `/influence/current` returns `{window,places:[{placeId,boosts,reductions,yourBoosts,yourReductions}]}` for the next betting market, including zero counts for active restaurants. `window` is the same saved betting window, including `cutoffAt` (ISO UTC), local cutoff date/time and `open`. The read takes the settings lock and shares market creation/expiry cleanup with betting, so it may append refunds for expired markets. Counts represent outstanding units on that draw, not historical purchase totals.

POST `/influence/current` requires identity, matching Origin and UUID `Idempotency-Key`. Body `{localDate,placeId,action:'boost'|'reduce',change:1|-1}` stages or withdraws exactly one unit. Returns `{place,balance,tokenDelta}`; negative token delta is a charge, positive is a refund. Additions first cancel one owned opposite-direction unit with an original-price refund; otherwise they buy a unit using current economy settings. Each person has one signed position per place and market. Older opposing pairs are refunded on their next adjustment before cutoff. Withdrawals reverse the newest matching owned unit's saved logarithmic multiplier and refund its original price. Both directions are editable only strictly before the saved market cutoff; closed/stale dates return 409 `INFLUENCE_CLOSED`. Missing owned units return a conflict. Every edit appends a ledger entry and stores its replay receipt; existing keys return the original response without reapplying effects, including after cutoff. POST `/purchases` with boost/reduce remains a compatibility route for staging one unit under the same cutoff; remove remains an immediate final purchase. Adding/banishing places cannot be undone through influence controls. After a draw, its unit effects remain permanent. No historical editable units are inferred from pre-migration purchases.

Schedule changes/expiry, participant deactivation and restaurant banishments append original-cost refunds for affected pending units and reverse their saved effects. Banishments also refund all open stakes for that restaurant, including requests locked at cutoff but not yet drawn; unrelated places are unchanged. Admin exact-odds updates refund pending influence before applying the new distribution.

Use 201 for newly created resources and 200 for reads/actions/replays; deletes and session changes use 204. Use 400 for invalid schemas, 401 for missing identity/session, 403 for inactive identity or failed origin check, 404 for unknown resources, 409 for duplicate names, idempotency mismatch, already-claimed attendance, insufficient balance, or closed attendance window, and 503 for unavailable persistence. Application-specific codes make errors distinguishable.

`todayResponse.odds` always describes the current wheel for the next uncommitted draw. `result` is today's committed historical choice or null. Empty-wheel and unscheduled states are explicit. Never expose a mutation that accepts a client-selected winner.

`todayResponse.wheel` is `{mode:'upcoming',localDate:'YYYY-MM-DD'}`, computed on the server in the schedule timezone. Once today's result commits, it immediately targets the next scheduled date (Friday to Monday for weekdays); with no result it retains today's pending draw, even if delayed. Skipped dates are excluded. The contract still accepts legacy result mode for compatibility, but the server no longer emits it. The UI shows live odds except during the current animation, winner dialog or explicit replay, and returns to live odds when the dialog closes. It does not persistently display the previous winner. Polling and animation timing are unchanged.

Draw results include the saved `timezone` and `snapshot` entries (`placeId`, `name`, `logWeight`, `probability`) from before decay. The UI animates these committed segments while showing current odds and spending controls separately. Wallet responses include `balance`, newest-first `ledger` entries (`id`, `delta`, `kind`, nullable `reason`, UTC `createdAt`, nullable `placeId`, `placeName`, `betId`, `betLocalDate`), and `bets` containing that person's current and historical `betView` records. Ledger restaurant targets come from each entry's own restaurant reference, so later bet edits cannot change the target shown for an earlier reservation. Restaurant names resolve retained restaurant records; they are current names rather than immutable purchase-time name snapshots. Legacy saved correction receipts may omit these added fields; the wallet schema supplies nulls and an empty bets array when parsing them.

GET `/activity?date=YYYY-MM-DD&scope=day|draw` → `dailyActivityResponse`, with a valid active `X-Participant-Id`. Date is optional and defaults to the current day in the configured workplace timezone; invalid dates return 400. Returns `{localDate,timezone,entries,bets,positions}` from one read-only repeatable-read snapshot. The optional scope defaults to `day`: entries use the workplace calendar date of the action. In `draw` scope, entries include bet/influence ledger rows linked to a market on the selected draw date, regardless of when tokens moved. Unlinked historical wheel purchases are included by their inferred target draw date, exposed as optional inferredDrawLocalDate. The Activity UI always requests draw scope, labels its selected spin date, and labels historical attribution as inferred; they do not create editable draw positions. Token transfers are also attributed read-only to the next actual draw after their timestamp, falling back to the next scheduled draw; both ledger sides retain their shared `transferId`, counterparties, amounts and original timestamps. Other unlinked actions remain available in day scope. Bets, positions and health bonuses always use the selected draw date, without substituting the upcoming date for today. Entries contain the same ledger fields plus `participantId`/`participantName` for every action in the requested scope, including archived participants and restaurants; influence entries expose optional `influenceLocalDate` and refunds have `boost-refund`/`reduce-refund` kinds. Bets contain `betView` plus participant details for the selected **scheduled draw date**, including open, won, lost, cancelled and refunded states. Positions group nonwithdrawn units by person/restaurant for that draw date: `{participantId,participantName,placeId,placeName,boosts,reductions,boostTokens,reductionTokens,status:'staged'|'locked'|'committed'}`. Refunded requests are excluded; settled units show as committed. These are latest saved positions, not a complete history of place-only bet edits. Entries and positions/bets have different date meanings: tokens spent today may influence a future draw. This read does not create markets, refund stakes, draw winners or write game state. Purchase charts show gross boost/reduce spending before refunds; the position chart shows the outstanding units. Neither reconstructs historical odds. Activity bet rows additionally return nullable `currentProbability` and `estimatedWinPayout`: for open bets these use live active-place weights from the same read snapshot; estimated payout includes the stake and is `min(2147483647, floor(stake / probability))`. Zero/unavailable chances have no estimate. Closed bets have null live quotes and retain their saved settlement probability/payout.

All state changes require an Origin header exactly matching `APP_ORIGIN`, including identity selection and login. Admin login allows eight attempts per fifteen-minute window in a bounded process-local limiter, returns 429 when limited, and clears attempts after successful authentication. Use one web instance or add a shared edge limiter before scaling. Session lifetime is eight hours; missing/short session secrets fail closed.

Push subscriptions validate browser service hosts (Google, Mozilla, Apple, Windows), HTTPS without custom ports/credentials, and browser key shapes. Deleting a subscription deactivates it and its pending jobs while preserving referenced history. Reusing an endpoint with a new participant or keys retires stale pending jobs.

POST `/influence/refund` requires identity, matching Origin and UUID `Idempotency-Key`. Body `{localDate,placeId}` refunds all the caller’s outstanding units on that spot before the saved cutoff, returning `{place,balance,tokenDelta}`. Bets and other people’s units stay intact. Identical retries replay the saved response after cutoff.

PUT `/admin/place-weights` requires admin authorization and matching Origin. Body `{placeId,weight}` accepts a finite positive relative weight. It refunds pending influence before storing `Math.log(weight)` and returns the updated place. Percentage editing remains available through the existing restaurant odds API.

Compatibility POST `/purchases` responses use nonnegative `spentTokens`; an opposite-direction cancellation returns `spentTokens:0` plus `refundedTokens` with the refunded original cost. No new opposite unit is bought in that request.

Market windows additionally expose nullable optional `opensAt`. When `postDrawDelayMinutes` is positive, `opensAt` is the latest committed draw timestamp plus that delay, and `open` remains false until then (also subject to the saved cutoff). At the default 0, `opensAt` is null and activity opens immediately. Delays continue across midnight. Influence/bet mutations reject edits during that pause through their existing closed errors. Paid restaurant additions/removals reject the same period with `409 WHEEL_ACTIVITY_PAUSED`. Successful idempotent retries still replay their original receipts. Calendar activity preserves original action dates; draw activity uses recorded market links or `inferredDrawLocalDate` for unlinked wheel purchases (boost, reduce, add-place, remove-place). Derived dates use the first actual subsequent draw, falling back to the current schedule/skip when no later draw is recorded. A post-roll purchase therefore appears on the next scheduled draw. This read-only attribution neither rewrites history nor creates editable positions.

GET `/token-overview` requires an active `X-Participant-Id` and returns `{localDate,spinLocalDate,timezone,rows}` in a read-only repeatable-read snapshot. Rows contain `{participantId,participantName,balance,totalBalance,rank,spinDelta}` for active members. `balance` is uncommitted ledger balance; `totalBalance` adds open bet stakes on open markets and nonwithdrawn influence token costs on open markets, including locked positions. Settled, withdrawn, refunded and unlinked historical purchases do not add to total. Rows sort by total descending, then name; equal totals have the same competition rank (1, 1, 3). `spinLocalDate` is the current betting target, using the same schedule, committed-result and skip rules as Activity. `spinDelta` replaces `todayDelta` and sums exactly the draw-scoped Activity entries for that spin, including actions on earlier days, linked bets/refunds, inferred historical wheel purchases and sent/received token transfers. Other wallet activity without a target spin is excluded from this column, while Total and Uncommitted remain current wallet totals. Midnight, the betting cutoff and a configured post-roll pause do not reset the spin delta; committing or skipping a draw advances its target. Reads never create markets, expire reservations or modify balances.

Lunch spot counts in GET `/influence/current` include older unlinked boost/reduce purchases attributed to the current market's spin date by the same logic as draw-scoped Activity. Team `boosts` and `reductions` sum unwithdrawn current-market lots plus those historical purchases once per ledger purchase. Each position adds `historicalBoosts` and `historicalReductions` (nonnegative integers, default 0 when parsing older responses) to identify the historical subset. `yourBoosts` and `yourReductions` remain strictly the caller's refundable unwithdrawn lots. Linked debit rows are not counted again and withdrawn lots remain excluded. No influence lots, ledger links, weights or refund rights are reconstructed for historical purchases. Historical purchases for other spins are excluded.
